## Description

MeshCore-BTC is a general-purpose bot framework for [MeshCore](https://github.com/liamcottle/meshcore.js) LoRa mesh
radios, connected over USB serial to a device running the Companion USB firmware. The framework itself only handles
the connection, message dispatch, rate-limited sending and a crash/hang watchdog - all actual behavior lives in
small, independent **modules**. Two ship out of the box:

- **`bitcoin`** - broadcasts a daily Bitcoin price update (with trend indicator, Fear & Greed Index, network
  hashrate and Aave borrow rates) to a public channel.
- **`ai`** - answers direct messages and (optionally) channel messages using a locally-running
  [Ollama](https://ollama.com) model.

## Architecture

```
index.mjs                  Thin bootstrap: loads config, wires up modules, starts the bot
core/framework.mjs         Connection lifecycle, message normalization, dispatch, ctx factory
core/send-queue.mjs        Global FIFO send queue with min-gap rate limiting
core/watchdog.mjs          Activity watchdog (exit 42 on a hung connection)
modules/bitcoin.mjs        Daily Bitcoin price broadcaster
modules/ai.mjs             Ollama-backed DM/channel responder
utils.mjs                  Shared helpers (byte-safe string truncation/splitting, JSON persistence, retry, alarms)
run.sh                     Supervisor loop - restarts index.mjs whenever it exits
config.json                Your local configuration (gitignored - copy from config.json-example)
config.json-example        Annotated example configuration
price-history.json         Auto-generated by the bitcoin module, stores the last price for trend comparison
```

**Core responsibilities:**

- **Connection** (`core/framework.mjs`): opens the transport (serial today; the `transport.type` config key is a
  seam for adding others later, e.g. TCP), waits for `connected`, fetches self identity and the channel list, then
  initializes every enabled module with a `ctx` object.
- **Dispatch** (`core/framework.mjs`): on every `MsgWaiting` push from the device, drains all waiting messages,
  normalizes each into a plain `{ kind: 'channel' | 'direct', ... }` object, and calls the matching hook
  (`onChannelMessage` / `onDirectMessage`) on every module in turn. One module throwing does not stop the others or
  crash the bot.
- **Send queue** (`core/send-queue.mjs`): every outgoing message - from any module - goes through one shared FIFO
  queue with a minimum gap between transmissions (`sendIntervalSeconds`), so modules never need to think about
  airtime pacing themselves.
- **Watchdog** (`core/watchdog.mjs`): see [Watchdog](#watchdog--auto-restart) below.

## Requirements

- Node.js 22 or higher (LTS recommended)
- MeshCore device with Companion USB firmware connected to the computer
- For the `ai` module: [Ollama](https://ollama.com) running locally (or reachable over the network) with the
  configured model already pulled

## Installation

```sh
git clone https://github.com/jooray/MeshCore-BTC.git
cd MeshCore-BTC
npm install
cp config.json-example config.json
# edit config.json - see Configuration below
```

## Usage

```sh
# uses the "port" from config.json
node index.mjs

# or override the serial port on the command line
node index.mjs /dev/ttyACM0

# recommended for production: auto-restarts on crash or watchdog exit
./run.sh
```

## Configuration

`config.json` (copy from `config.json-example`, it's gitignored):

| Key | Default | Description |
| --- | --- | --- |
| `port` | - | Serial device path. Overridden by a command-line argument if given. |
| `transport.type` | `"serial"` | Transport used to reach the device. Only `"serial"` is implemented today. |
| `watchdogTimeoutMinutes` | `360` | Minutes of connection inactivity before the bot exits with code 42 for `run.sh` to restart it. |
| `sendIntervalSeconds` | `15` | Minimum gap between any two outgoing messages (channel or direct), across all modules. |
| `limits.channelMessageBytes` | `155` | Max UTF-8 byte size of a single channel message. |
| `limits.directMessageBytes` | `160` | Max UTF-8 byte size of a single direct message. |
| `modules.<name>` | `true` | Set to `false` to disable a module without removing its config. |
| `bitcoin.channel` | falls back to `channels.bitcoin` | Channel name to broadcast to. |
| `bitcoin.alarm` | falls back to `bitcoinAlarm` | Daily broadcast time, `"H:MM"` or `"HH:MM"` (local time). |
| `bitcoin.priceFile` | - | Path to the JSON file used to remember the last price (for the trend emoji). |
| `bitcoin.showFearGreed` | - | Include the Alternative.me Fear & Greed Index. |
| `bitcoin.showHashrate` | - | Include the Blockchain.info network hashrate. |
| `bitcoin.showBorrowRates` | - | Include EURC/USDC variable borrow rates from Aave (needs `ethereum.*`). |
| `ethereum.rpcUrls` | - | Ethereum JSON-RPC endpoints to try, in order, for `showBorrowRates`. |
| `ethereum.aavePoolAddress` | - | Aave v3 Pool contract address. |
| `ai.ollamaUrl` | `http://localhost:11434` | Base URL of the Ollama server. |
| `ai.model` | `gemma4:12b-mlx` | Model name, must already be pulled in Ollama. |
| `ai.requestTimeoutSeconds` | `120` | Abort a single Ollama call after this many seconds (no retries). |
| `ai.historyLength` | `6` | Number of past exchanges (user+assistant pairs) kept per conversation, in memory. |
| `ai.maxParts` | `3` | Max number of numbered parts a reply may be split into. |
| `ai.channels` | `{}` | Map of channel name -> `"mention"` or `"all"` (see below). Channels not listed are ignored. |
| `ai.systemPromptExtra` | `""` | Extra text appended to the system prompt (house rules, persona, etc). |

The legacy top-level keys `bitcoinAlarm` and `channels.bitcoin` from the pre-refactor config still work as
fallbacks, so an old `config.json` keeps functioning as-is.

## Message format (bitcoin module)

```
📈 BTC: 94 500 EUR
Fear/Greed: 73 (Greed)
Hashrate: 850 EH/s
```

📈/📉 reflects the trend since the previous broadcast, tracked in `price-history.json`.

## AI module

The `ai` module answers questions by forwarding them to a locally-running Ollama model and posting the (trimmed)
reply back to the mesh.

- **Direct messages**: always answered, for any contact the device can resolve (unknown senders are skipped and
  logged, not answered).
- **Channel messages**: only for channels listed in `ai.channels`:
  - `"mention"` - only replies when the bot's own name appears (case-insensitively) anywhere in the message; the
    mention itself (and a leading/trailing `@`, if present) is stripped before the text is sent to the model.
  - `"all"` - replies to every message in that channel that wasn't sent by the bot itself.
  - Channels not present in the map are ignored entirely.
- **Length budgeting**: LoRa airtime is scarce, so replies are kept under the configured byte limit
  (`limits.channelMessageBytes` / `limits.directMessageBytes`). This is a **byte** budget, not a character one -
  emoji and accented characters take 2-4 bytes each in UTF-8, and truncation always cuts on a valid UTF-8 character
  boundary, never mid-character. If a reply genuinely can't fit in one message, it's split into up to `ai.maxParts`
  parts, sent in order and numbered `"1/2 ..."`, `"2/2 ..."`, etc. If even that isn't enough, the remainder is
  hard-truncated (content is lost, and this is logged).
- **History**: kept in memory only, per contact (DMs) or per channel, capped at `historyLength` exchanges. **A
  restart wipes all conversation history** - this is deliberate, not a bug, to keep the module simple and stateless
  on disk.
- **Requires Ollama**: a reachable Ollama instance with the configured model already pulled
  (`ollama pull <model>`). If Ollama is down, times out, returns an HTTP error, or returns an empty reply: direct
  messages get a canned `"AI unavailable right now"` reply; channel messages fail silently (logged only, to avoid
  spamming shared airtime with error noise).

### Warnings

- **`"all"` mode bot-loop risk**: if two bots with `"all"` mode are on the same channel, they can end up replying to
  each other indefinitely, burning airtime. Prefer `"mention"` mode on shared/public channels, and never point two
  `"all"`-mode bots at the same channel.
- **Sender-prefix parsing is an assumption**: MeshCore channel messages are assumed to arrive as `"SenderName:
  message"` text (this isn't formally documented by the library). The framework parses this defensively - if a
  message doesn't match the pattern, it's treated as having no sender name rather than crashing - and always logs
  the raw channel message at debug level so the assumption can be verified against real traffic.

## Watchdog / auto-restart

The MeshCore serial link can go silent without throwing an error (device hang, USB glitch). `core/watchdog.mjs`
listens for the connection's `'rx'` event (any received frame) and `'connected'`, and tracks the timestamp of the
last one seen. A 60-second timer checks the idle time; once it exceeds `config.watchdogTimeoutMinutes` (default
360 = 6h), it logs a `WATCHDOG:` message and calls `process.exit(42)`.

Exit code `42` has no special meaning to Node itself - it's just how the bot communicates "I gave up, please
restart me" to whatever is supervising it. `run.sh` is that supervisor: it loops forever, restarting `node
index.mjs` after any exit (watchdog-triggered or otherwise) with a 10s delay, logging the exit code and timestamp
each time. Run the bot via `./run.sh` in production instead of calling `node index.mjs` directly.

Trade-off: a mesh that is genuinely and completely silent (zero RX frames received, e.g. nothing at all in range)
for the full timeout window will also trigger a restart, even though the connection itself would be fine. In
practice a live MeshCore mesh essentially never goes that quiet, and a restart in that scenario is harmless.

## Writing your own module

A module is a plain object, default-exported from a file in `modules/`:

```js
{
  name: 'my-module',                       // required, used as the config key and log prefix
  async init(ctx) { ... },                 // optional, called once after the device connects
  async onChannelMessage(msg, ctx) { ... },// optional
  async onDirectMessage(msg, ctx) { ... }, // optional
}
```

Register it in `index.mjs`:

```js
import myModule from './modules/my-module.mjs';
const modules = [bitcoin, ai, myModule].filter(m => config.modules?.[m.name] !== false);
```

### The `ctx` object

Each module gets its own `ctx`, passed to `init`, `onChannelMessage` and `onDirectMessage`:

| Field | Description |
| --- | --- |
| `config` | The full parsed `config.json`. |
| `moduleConfig` | Shorthand for `config[module.name] ?? {}`. |
| `self` | `{ name, publicKey }` - this device's own identity. |
| `limits` | `{ channelMessageBytes, directMessageBytes }`. |
| `log(...)` / `logError(...)` | `console.log`/`console.error`, prefixed with `[module-name]`. |
| `utils` | The `utils.mjs` namespace (formatting, byte-safe truncation/splitting, retry, etc). |
| `getChannelByName(name)` / `getChannelByIdx(idx)` | Look up a channel, returns `{ channelIdx, name }` or `null`. |
| `sendToChannel(channelIdx, text)` | Truncates to `limits.channelMessageBytes` and enqueues; resolves after the message is actually sent. |
| `sendToContact(publicKey, text)` | Same, truncated to `limits.directMessageBytes`. |
| `registerAlarm(timeHHMM, cb)` | Calls `cb` once a day at the given local time (`utils.setAlarm` under the hood). |
| `connection` | Escape hatch to the raw `meshcore.js` connection, for anything not covered above. |

### Normalized message shapes

`onChannelMessage(msg, ctx)` receives:

```js
{
  kind: 'channel',
  channel: { channelIdx, name },   // name may be null if the channel couldn't be resolved
  text,                            // raw message text, exactly as received
  senderName,                      // parsed from a "Name: body" prefix, or null
  body,                            // text with the "Name: " prefix stripped, or == text if no match
  fromSelf,                        // true if senderName matches this device's own name
  raw,                             // the raw channelMessage object from meshcore.js
}
```

`onDirectMessage(msg, ctx)` receives:

```js
{
  kind: 'direct',
  contact,        // resolved contact object from meshcore.js, or null if unknown
  senderName,      // contact?.advName ?? null
  pubKeyPrefix,
  text,
  raw,
}
```

### Example module

A tiny module that replies "pong" to any direct message containing "ping":

```js
export default {
  name: 'ping',

  async init(ctx) {
    ctx.log('ready');
  },

  async onDirectMessage(msg, ctx) {
    if (!msg.contact) return;
    if (!msg.text.toLowerCase().includes('ping')) return;
    await ctx.sendToContact(msg.contact.publicKey, 'pong');
  },
};
```
